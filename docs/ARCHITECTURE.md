# rules_dart — Architecture & Design

## Overview

`rules_dart` is a Bazel rule set for the Dart language. It:

- Downloads published Dart SDK releases (not building from source)
- Uses bzlmod exclusively, targeting Bazel 9.x
- Is designed for extension by other rule sets, such as `rules_flutter`

---

## Provider Design

| Provider                  | Level        | Purpose                                                                                                                                         |
| ------------------------- | ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `DartSdkInfo`             | Toolchain    | The `dart` binary, version, the SDK's files, whole (`files.all`) and by use (`files`, a `DartSdkFilesInfo`)                            |
| `DartInfo`                | Library      | Its own packages, srcs, deps and indirect_deps, transitive_srcs, transitive_src_dirs, transitive_resources, transitive_packages, transitive_code_asset_files, analyzer summaries |
| `DartPackageInfo`         | Metadata     | One package's name, package_root, version, language version, code and data assets, unreplaced build-hook path, link hook and the assets it promises, license file (in DartInfo depsets) |
| `DartPackageMetadataInfo` | Declaration  | A package's facts as its `dart_package_metadata` states them, and its root, read back through `package` by every target of that package |
| `DartAnalyzableInfo`      | Executable   | An executable's analyzable closure: a nested `DartInfo`, plus its own entrypoint sources                                                        |
| `DartPackageConfigInfo`   | Build action | Generated package_config.json file                                                                                                              |
| `DartCompileInfo`         | Binary       | Compiled output file, compile_mode string                                                                                                       |
| `DartRecordedUsesInfo`    | Binary       | The uses of `@RecordUse` definitions the compiler recorded (`file`), and whether it could (`kind`: `aot` or `empty`)                            |
| `DartCodeAssetInfo`       | Asset        | One native code asset: asset id, link mode, dynamic library or system URI                                                                       |
| `DartDataAssetInfo`       | Asset        | One data asset a `dart_data_asset` declares: `package`, `name`, `file`, `id`; no bundling paths                                                 |
| `DartProgramAssetsInfo`   | Program      | What one program ships, linked or not: the data and code assets known at analysis time by id, and each link hook's output                                |
| `DartModuleInfo`          | Aspect       | A target's compiled kernel modules, their outlines and manifests, and its dependencies'                                                         |
| `DartImportCheckInfo`     | Aspect       | The import check results of a target and its dependencies                                                                                       |
| `DartKernelSdkInfo`       | Platform     | The compiler and platform files one kernel target compiles with (see [Dart Compilation Model](#dart-compilation-model))                         |
| `DartAnalysisOptionsInfo` | Analysis     | An `analysis_options.yaml` and the packages its `include:` directives resolve against                                                           |

**DartInfo contains zero Flutter concepts.** `rules_flutter` wraps/extends it, never modifies it.

**A library contributes its packages, usually one.** `DartInfo.packages` holds the `DartPackageInfo` records of the packages a target itself contributes: one for a library, none for a target that only groups others (`dart_info_no_package()`), and several for one library pub generates. Pub allows packages to depend on each other (`dio` imports `dio_web_adapter`, which imports `dio`); Bazel does not allow a dependency cycle, so such packages are one target, and each keeps its own name, `package_root` and language version. Nothing downstream needs to know: `package_config.json` lists records, a module compile splits a target's sources into modules by their imports whatever packages they belong to, and the layering check accepts every package a direct dependency contributes, which is why `DartInfo.deps` maps each dependency to the names of all its packages.

**One package name can reach a target through several records, and they must agree.** A package split across `dart_library` targets, one per directory of its `lib/`, reaches a target as one record per target; two pub hubs independently supplying one package — rules_flutter's `flutter.pub()` and rules_dart's `pub.from_lock()` both generating a spoke for `ffi` — reach it as one record per hub. Records rooted at one directory are one producer's targets of one package, and must name the same `dart_package_metadata` (`DartPackageInfo.metadata`); one naming another, or none, fails the build naming each declaration and a target naming it, and nothing else is reported, since that is the cause of any value they disagree on. Records rooted apart are compared by value: `merge_package_records` makes them one record, the first, for source resolution, with every package-level fact — `version`, `language_version`, `license_file`, `link_hook`, `link_hook_assets`, `unreplaced_hook` — taken from whichever record states it, and code and data assets unioned. A record that states a fact and one that states none do not conflict; the one that states nothing knows less, as a `dart_library` written by hand does. Two records stating different values do conflict, and `package_agreement_error` fails the build naming the target behind each (the record's `label`) and its root: kept quietly, dependency order would decide which version's sources compile, which Dart semantics apply, which hook runs. Files are compared by their path within the package, so two hubs fetching one archive agree. A target that is itself a package — a downstream app whose sources are its package's `lib/` — contributes one record in place of the libraries' records at its root, built by `merged_package_record` from the declaration it names, merged with theirs.

**A package's facts are stated once, on `dart_package_metadata`, and every target of the package names it.** A package's name, language version, version, license, build and link hooks and code and data assets describe the package, not a rule, as its `pubspec.yaml` and `hook/` do upstream, and a package is routinely built by several targets — libraries per directory, a `dart_codegen` producing part of it, its tests and binaries — sometimes in different BUILD files, where no macro can hold them together. Stated on one of those targets, a fact reached only programs that reached that target: a test importing another directory's library saw no build hook, and a language version stated on the second record was dropped when the first stated none. So the facts live only on `dart_package_metadata`, Bazel's shape for package-level metadata (a target the others point at, as `default_package_metadata` is), and `dart_library`, the codegen rules and macros, the executables and `pub_package_member` take `package` naming it and no inline fact. Every record is built from the declaration (`package_info_from_metadata`), so every record carries every fact. A target naming none is named after its root directory (`derive_package_name`) and states nothing else. **A package has exactly one declaration, as it has one `pubspec.yaml`, and two are refused where they meet.** Its name is free and it may sit in any BUILD file of the package: it declares the package rooted at its directory, or, under `lib/`, at the directory above that `lib` (`locate_package_root`), as a `dart_library` there belongs to that root. A second declaration for one root, in the same BUILD file or another, is refused wherever targets naming the two meet, as rules_go refuses two libraries of one import path in a binary: `merge_package_records` fails when records at one root name different declarations, whatever package names they state, naming each declaration and a target naming it. It runs for every program and test (`program_packages`), every analysis (the `dart_analyze` aspect), and every library through its import check, which assembles a package config from the library's closure, so a library reaching both fails though no program uses it. A fixed name would stop a second in one BUILD file, but not one in another, and would be a symbol rules must know rather than a target they point at. Facts that differ between libraries of a package are not package facts: native assets that differ between programs are the `code_assets` of the executable, which replace the package's by id. The root a declaration declares is the package root, as the pubspec's directory is upstream; the hook locations are checked against it, and a library's sources must lie under its `lib/`. A codegen rule returns the declaration it names, and `codegen_identity_error` checks it against the library collecting its output at the one point the two meet, that library's `srcs`. Pub spokes and the SDK's kernel packages write a `dart_package_metadata` too, so generated code has the same shape; `DartPackageInfo(...)` remains the constructor for a rule set whose rules state a record's facts themselves. Another rule set declares `package` the same way, from the same code: it merges `package_identity_attrs()` (`mandatory` and `doc` for a rule that requires `package`, or says more of it) into its library rule's `attrs` and calls `library_package(ctx, srcs, resources)`, which resolves the declaration, checks its files against the root and returns the record `dart_library` would build, so the check cannot be skipped. An executable calls `resolve_package_identity(ctx)`, or `resolve_package_identity(ctx, metadata = ...)` when the declaration comes from another target (a test built in its application's package), which returns the declaration's facts with the package's `package_root` and `license_file`, and `executable_package_record(ctx.label, identity)` for the record, rooted at the declaration's package root wherever the target is, as `dart_binary`'s is (all in `//dart:utils.bzl`). Gazelle writes the declaration at each package root, as `pubspec-metadata`, from `pubspec.yaml`, `hook/` and the license file, adopts one already there whatever its name, fails on two there, and names it on every rule it writes.

**`DartInfo` means "valid as a dep"; `DartAnalyzableInfo` means "has Dart sources to analyze".** Every `deps` attribute in this rule set and in the ones built on it gates on `providers = [DartInfo]`, so which provider a target hands out is what decides whether it can be depended on. That is why `dart_binary`/`dart_test`/`dart_js_binary`/`dart_wasm_binary` deliberately provide only the second: an executable is not a dependency, Bazel has no negative provider constraint to say so, and returning `DartInfo` would silently make `dart_library(deps = [":some_binary"])` legal. The `dart_analyze` aspect accepts either, which is also what keeps `dart_proto_library` analyzable with no adoption work — the `DartInfo` branch is permanent, not a migration shim. A library needs nothing extra because for a library `DartInfo` already _is_ the analyzable closure and its `DefaultInfo` lists its own sources; an executable needs the wrapper because its `main` lives outside every package's `lib/`, so no `DartPackageInfo` can name it and no `package:` URI reaches it. The wrapper nests a `DartInfo` built by `dart_info()` (or `dart_info_no_package()`, for an executable with no package) rather than restating its fields, for exactly the reason `dart_info()` exists: a provider re-enumerating `transitive_srcs`/`transitive_resources`/`transitive_packages` would be a second place for a merge to be forgotten.

**An executable belongs to the package whose declaration it names, wherever its BUILD file is.** Upstream, a file belongs to the innermost package root containing it, `bin/` and `test/` included, and takes that package's language version. The root is where the pubspec is, so here it is the root the `dart_package_metadata` declares: an executable naming it with `package` is a member of that package, rooted at the declaration's package root, so a test in `pkg/test/BUILD.bazel` naming `//pkg:pubspec-metadata` compiles at the package's version with no directory-name convention and whether or not it depends on a library of the package (`executable_package.bzl`). Its `DartAnalyzableInfo` is built with `dart_analyzable_info`, so analysis and the format check read the version from its own record, and its record joins the package list it compiles against. Unset, the executable carries no package, and its entrypoint takes the version of a package its `deps` bring whose root contains it. `executable_package_error` refuses what would contradict its `deps`: an own file outside the package root, or inside a package in `deps` rooted deeper (Dart would give the file that package's version); a name that `deps` supply only at other roots (one package, one root — a name reached at several roots stays legal for dual pub hubs, provided one of them is this root); and another name at the same root (one directory, one package). A record of the same package naming another declaration is `merge_package_records`'s error, as for any two records. A package in `deps` whose root merely contains the executable's under another name is a nested package — a pub package's `example/` — and Dart gives the nested one's files its own version, so that is allowed. Generated `srcs` it collects are checked with `codegen_identity_error`, as for a library.

**Read `DartInfo` directly; build it through `dart_info()`** (`//dart:utils.bzl`). Rule sets outside rules_dart produce `DartInfo` too — `rules_flutter`'s `flutter_library`, `rules_dart_proto`'s `dart_proto_library` — and constructing it by hand means enumerating every field and merging every transitive depset one at a time. That made each added field a breaking change for all of them, and left each to work out independently how the new field merges. `dart_info()` takes what a target contributes itself — its package records, built from its declaration (above), and its own files — and merges its dependencies' closures internally, so a new field is a change to one function. It also declares the library's analyzer summary (see below), which is why it takes the rule's `ctx` and the rule declares `SUMMARY_ATTRS`, `PORTABLE_EXEC_GROUPS` and `COPY_TO_DIRECTORY_TOOLCHAINS`. It also removes a failure that is invisible in review: a missing field's correct fix (forward the dependencies' values) and its tempting fix (declare it `depset()`) look identical in a diff, and the second silently drops every dependency's contribution at that boundary. A target that deliberately ships no package of its own — `flutter_material_icons` carries a font and no Dart — calls `dart_info_no_package()` instead: it merges its dependencies' closures the same way, and contributes no package record. The same hazard applies to _copying_ a `DartPackageInfo` with a field overridden, so rules_dart routes that through one internal `derived_package_info()` rather than restating the field list at each call site; a copy that forgets a field drops it only for the targets that take that path, which is harder to spot than losing it everywhere.

## Dart Compilation Model

A `dart_test` is built the way Dart's own modular build (`build_modules`) builds a program, in Bazel's terms: libraries are compiled once into kernel modules, the entrypoint is compiled against the modules it reaches, and those are linked.

- **Modules.** `dart_module_aspect` (`dart/private/dart_module.bzl`) runs over every `DartInfo` target. Its own sources (`DartInfo.srcs`) are split as `build_modules`' fine strategy splits a package: one module per strongly connected component of their imports, with conditional imports decided for the platform from its `libraries.json`. Its coarse strategy, which merges private libraries into the public library that reaches them, is not used: it would make a leaf unusable wherever that public library is unsupported. One action per target compiles every module with the SDK's `kernel_worker`, kept running between modules, against the modules of the target's direct dependencies (`DartInfo.deps`). The output is a directory of `.dill`s and a manifest naming each module's libraries, its imports and whether it compiled. Which attribute a dependency arrived through is the rule's business — `dart_proto_library` keeps its Dart deps in `dart_deps` — so the aspect follows every attribute that is not a tool, plus the toolchains a rule lists in `_dart_toolchain_types`, and matches what it reaches against `DartInfo.deps`; a toolchain hands on the libraries it holds.
- **Broken modules fail only what reaches them.** A module that needs a `dart:` library the platform lacks (`dart:html` in a package that also runs on the web) is not compiled, and one that does not compile records its errors; neither fails the target. `build_modules` builds a module only when an entrypoint reaches it; Bazel's actions are fixed before any runs, so the same answer comes from compiling all of a target's modules once and failing only an executable that reaches a broken one, with that module's errors. A whole-program compile never read what nothing reached either.
- **Strict dependencies.** Bazel's addition: a library importing a package that none of its `deps` reach, or a file of its own package that no target it depends on holds, is an error at that library, whether or not anything reaches it — an import has to be declared, not supplied by whichever test happens to bring the package in. In another repository's targets (pub packages, whose dependencies are generated from their pubspecs) the same finding is recorded on the module instead.
- **Spellings.** Every `import`, `export` and `part` is judged as the compiler will resolve it, not as rules_dart canonicalises it, and must be a `dart:` library, a `package:` URI that stays inside its package and names a file a dependency provides, or a file the target holds (for a part, the target itself). Anything else is refused with the spelling to use: a `file:` URI or another scheme, which the compiler reads from wherever the machine has it; a relative path out of the workspace, or one climbing out of a package's `lib/`, where `package:` resolution clamps it to another file; and a relative path into a package's `lib/` from outside it (`../lib/x.dart` from a test), which the compiler loads as a second library apart from the `package:x/x.dart` its dependency's module holds. The module compile holds to its declared inputs on its own, in a persistent worker too (below); the check is what names the directive and the spelling to use.
- **Where the check runs.** It reads directives and nothing compiled, so it is one small `kernel_tool check` action per target, in the target's `_validation` output group, as rules_cc ties `layering_check` to the target: a `dart_library` checks itself, so any build of it — an analysis run included — checks it, and an executable checks its own files. `dart_import_check_aspect` checks the libraries of rules that cannot check themselves (`dart_proto_library`) for the executables reaching them. `kernel_tool`, which runs the check, is built from libraries too; the rule that builds it reaches them through a transition under which a library has no checker to depend on.
- **Layering.** A target of this repository may import only its own package and the packages of its direct `deps` (a source-less façade stands for everything it reaches), as in rules_go and rules_rust: a package reached only through a dependency's dependency stops being there when that dependency drops it. The front end would resolve such an import from the dependency's module regardless, so the import check enforces it — an executable's own files are compiled as modules too; a generated entrypoint is not checked. A rule whose sources are generated may name, in `dart_info(indirect_deps = ...)`, targets one of its deps depends on that the generator's output imports — `dart_proto_library`'s code imports the `fixnum` its protobuf runtime is built on — found by package in that dependency's `DartInfo.deps` rather than named by users, and checked at analysis to really be one. The `dart_layering_check` feature turns the check off for a target or a build, as rules_cc's `layering_check`.
- **Unused dependencies.** The converse of strict deps, in the same action: every entry of a target's `deps` must be named by an `import` or `export` of one of its files, on any branch, of its package's link hook, which is compiled from the package's dependencies, or of a file the rule writes and compiles with the target's. That last is an executable's `generated` (`import_check_output_groups`): `dart_test`'s bootstrap imports `package:test`, which the rule requires in `deps` to find the runner, so a test that reaches `package:test` only through a helper library, or has no cases, still uses it. A generated file is the rule's, not the author's, so its imports are uses but are not checked; a per-dependency exemption would not do, since `package:test` listed by a library and never imported is still unused. An unused edge compiles nothing in, but a change to the dependency rebuilds and reruns everything above it. A URI names the dependency holding that file; one no dependency holds (a package whose files are not listed, one a façade passes on) names each dependency contributing the package, else each façade reaching it, so only an edge whose removal leaves every import provided is reported. A dependency with files of its own that only reaches the package is not named: the layering check accepts no import through it, so it provides nothing the import may use. With the layering check off, any dependency reaching the package can provide it, and each is named. Only rules whose `deps` are what their sources import are judged: those that check themselves (`library_import_check`, which `dart_library` and `dart_package_cycle` call; the aspect skips any rule with `LIBRARY_IMPORT_CHECKER_ATTRS`) and the executables (`import_check_output_groups`). A rule left to the aspect states its dependencies for its own reasons: a `dart_proto_library`'s follow its `.proto` imports, some of them options its generated Dart never names. A codegen rule's `deps` are not judged: they are what a generator resolves against, and its only import check is that of a cycle's member sources it reads. Some dependencies work without an import: a Flutter plugin is registered by native code, so the app lists it and imports nothing of it. That is a fact about the plugin, not about each dependent, so the plugin's rule returns `DartUsedWithoutImportInfo` and the check never reports it wherever it is listed; Java's alternative, a `runtime_deps` attribute on every dependent, states per edge what the dependency already knows, and in Dart a plugin's library still joins the program (its registrant imports it), so it is not runtime-only. A dependency whose own package brings code or data assets or a hook is used by asset id and is not judged; one carrying no Dart at all (a font's `dart_info_no_package()`) has nothing to import and is not judged either. Shipping `resources` exempts nothing: a pub package's `resources` are whatever non-Dart files its `lib/` holds (a README, `dart fix` data), so `flutter` itself would be exempt, and a file read at run time by path is a `data` dependency, as in Bazel generally, which puts it in the runfiles. An exempt dependency is still listed to the check by its files, so an import of one names it, and not another dependency that only reaches its package. The message names the entry of the BUILD file that lists the deps. For a target a macro made, that is the macro call, found from Bazel's `generator_name`, so a `flutter_test` is named, not its `<name>.program`. Each dep is written as its dependent's BUILD file can write it: `:x` in the same package, `//pkg` when the name matches the package's last component, `@module//pkg` for another module. An apparent repository name is used only when `ctx.package_relative_label` confirms the target's own repository mapping gives it. Otherwise the canonical label is printed. That is the case for a dep reached through an alias, a pub hub's `@deps//:path_provider` say: Bazel resolves aliases before a rule sees its deps, so the rule sees only the actual target, in a repository the main module has no name for. A second action runs the same check and writes a JSON report of the unused deps instead of failing. It is the `dart_unused_deps` output group, beside `_validation` (`import_check_output_groups` returns both, and `library_import_check` too). Ordinary builds never request the group, so the report costs them nothing. `@rules_dart//dart/unused_deps` builds the group with validations off and edits the BUILD files from the reports. It asks `bazel query`, which reads BUILD files without resolving aliases, for the labels each entry wrote. It follows each alias's `actual` to the target the check judged, and finds the entry that states them. A written label goes when everything it resolves to is unused, so two aliases for one unused target both go. Every target an entry makes must agree: when a macro hands one `deps` to two targets, a dep goes only if each target that lists it found it unused, and a target the check does not judge keeps it. The fixer therefore also builds the reports of an entry's other targets, manual ones included. buildozer, a BCR module with prebuilt binaries, makes the edits, and rewrites the file in buildifier's format. It removes labels from list literals in the call, including lists joined with `+` and `select()` branches, but not from a list variable (`deps = SHARED + [...]`) or a call in a list comprehension. After the edit the fixer queries again. For each dep still listed it prints the place in the BUILD file and the entry, and exits 1, so the user removes it by hand if nothing else that uses the list needs it. `--dry-run` prints the buildozer commands and changes nothing. Gazelle users do not need the fixer. The check is on by default, as strict deps and layering are, and fails rather than warns, as every check here does; Gazelle writes `deps` from imports, so its BUILD files pass. The `dart_unused_deps` feature turns it off for a target, a package or a build, the only recourse for a dependency needed without an import whose rule does not say so.
- **Entrypoint and link.** The executable's own files are compiled into modules like any library's. Its entrypoint is generated — the `package:test` bootstrap, or a forwarder to the test's `main` — and compiled alone by `frontend_server` against the modules it reaches (joined into one file: separate `--import-dill`s cannot resolve an export across files), because that records `main`, which `kernel_worker` never does. `frontend_server` drops source positions from whatever it compiles against modules, so only the generated file's frames lose their line numbers. The link names the entry and exactly the modules it reached, entry first because the VM runs the first `main` a component names. For a test it writes a kernel list (`--@rules_dart//dart:kernel_list`, on by default): `#@dill` and a line per kernel, each the path from the list to the kernel in the runfiles tree, which the VM reads as the one program the kernels make together (`TryReadKernelListBuffer` in the VM's `dfe.cc`), so each module is stored once however many tests reach it, and the link reads only manifests. Those paths hold only where runfiles are a tree reached through the list's runfiles path; a manifest (Windows, or `rlocation` resolving to the output tree under `bazel run`) leads nowhere from them. So the launcher writes the list again at each run, under `TEST_TMPDIR` or a temporary directory it removes, naming each kernel where `rlocation` finds it (`@rules_dart//dart/kernel_list`, public, which also joins a list for a runner that takes one file: in a `memfd` filled by `sendfile` on Linux, a temporary file elsewhere). Nothing falls back to another way: a kernel missing from runfiles, a list that cannot be written, a library that cannot be placed, or a join that fails (the `memfd` included) is an error that says so and names `--@rules_dart//dart:kernel_list=false`. The VM resolves a code asset's `relative` path against the list's directory, so the launcher puts each library at the same runfiles-relative place beside the new list (a link; a copy on Windows) as it is beside the stored one. Off, the link concatenates the kernels into one `.dill`; concatenated kernel files are one valid kernel. A list makes every module directory the test sees a runfile, so a change to one the entrypoint reaches nothing in reruns the test, which a joined kernel's unchanged bytes did not. The link refuses a library compiled into two of them, except one package supplied by two pub hubs at two roots, where the first copy is kept.
- **Outlines, for early cutoff.** Modules and entrypoints compile against their dependencies' outlines, not their full kernels; only the link reads full kernels. The module action writes, beside each target's module directory, `<directory>.outlines`: the same files with function bodies and non-constant initialisers stripped, so an edit inside a body leaves every dependent's inputs as they were and Bazel reuses their compiles. The SDK has no VM outline: `kernel_worker --summary-only` refuses the `vm` target, and an outline written before the VM's modular transforms lacks what a dependent's transforms read. So the stripper (`dart/private/tools/kernel_outline.dart`) starts from the transformed full kernel and keeps, by an allowlist, what a dependent's compile reads: mixins (with `mixin class` and every class of a pre-3.0 library) whole and with their source positions, because the VM's mixin resolution copies their bodies into the dependent; constant constructors, fields and procedures, and the final fields of classes with a constant constructor, for constant evaluation; redirecting factories, default values and annotations; and the members the FFI transform generates on `Struct`, `Union` and `AbiSpecificInteger` subclasses, which dependents' FFI transforms look up. Anything it does not recognise fails the build. Positions and line tables are kept only for files declaring mixins, so an edit that moves code in such a file still recompiles its dependents. `pkg/kernel` reads only the kernel format of the SDK it ships in, so the stripper is built on the `pkg/kernel` of the same SDK as the compiler, unmodified: a `dart_kernel_source` repository fetches the source archive of the SDK's release tag (pinned in `versions.bzl` as `SOURCE_VERSIONS`) and builds the stripper on its `pkg/kernel`. The `dart` extension makes one per toolchain it registers, and registers it, as a `dart_outline_toolchain` of that SDK's version, under `//dart:outline_toolchain_type`; the VM's `vm_kernel_sdk` resolves it beside the Dart toolchain and fails unless both are of one version, naming the flag that turns outlines off. A Dart SDK of one's own registers its own outline toolchain; rules_flutter declares a `dart_kernel_source` of the Dart its Flutter SDK bundles, or, for an engine built from source with no release to pin, one with `path` set to the engine's `third_party/dart`: the repository then links `pkg/kernel` and `pkg/_fe_analyzer_shared` from that checkout, watches them so an edit refetches it, and is not reproducible. That body is `fetch_dart_kernel_source(rctx, path, prefix)` (`dart/repositories.bzl`, public), which a repository rule that already reads the checkout calls to write the two packages and the package holding `:outline_tool` below a `prefix` of its own repository, touching no other path (its root `BUILD.bazel` among them), and which returns the stripper's label relative to that repository; the caller marks itself not reproducible. `dart_kernel_source` itself is that function with no prefix for a `path`, and for a release the same BUILD-writing step over the extracted archive, so the packages and the stripper are declared in one place. The stripper reads only the kernel format of the checkout it is built from, so that checkout must be the one whose compiler writes the kernels. With the flag off the stripper is neither built nor fetched. `//dart/tests/outline_fixture:outline_guard_test` (in the `deep` tier) requires every module compiled against outlines to be byte-identical to one compiled against full kernels over the constructs listed. An entrypoint's compile also tells Bazel which dependencies' module directories it reached nothing in (`unused_inputs_list`), so a change to one of those does not rerun it; a directory is a single input to Bazel, so one reached in part stays an input whole. The platform's `DartKernelSdkInfo.outline_tool` decides: a platform with none compiles against full kernels.
- **The module worker reads only declared inputs.** The module action runs as a persistent worker that keeps one `kernel_worker` process across targets; the compiler's state is reused only between the modules of one request, keyed by the inputs' digests. Unless Bazel sandboxes it (dynamic execution, path mapping, `--worker_sandboxing`), the worker runs in the exec root, where a lookup under each kernel root would find files no request declared: a sibling the target does not hold, or a stale output in `bazel-out` shadowing the declared source at its path. So each request's compiler gets its roots in a fresh directory holding only that request's declared sources and package config (links to them; copies on Windows, where links need privileges), and a module naming a `file:` URI, which the compiler reads from the host whatever the build declares, fails without being compiled. A request's result then depends only on what it declares, as in a sandbox or on a remote executor.
- **Defines** are configuration. A test's own `defines`, and any a rule built on these modules derives from its other attributes (`executable_defines_config`), reach its dependencies through a transition, so modules are compiled — and cached — per set of declarations; a test with none shares the ordinary configuration. The test reads the same configuration back for its own compile, and that compile fails if a dependency's modules were compiled in another, so the entrypoint and its modules cannot disagree. A rule nothing of which is compiled Dart resets it on its incoming edge (`non_dart_transition`), so a code generator or code asset below tests with different declarations is configured once.
- **One kernel per platform.** A module is only valid for the platform it was compiled against, so the aspect is a factory over `DartKernelSdkInfo` (target name, compiler and `aot_runtime`, a platform dill and fixed declarations per kind of runtime, `libraries.json`): rules_flutter makes its own for Flutter, and shares the rest. The whole-program compile takes the same provider (`dart_whole_program_kernel_action`), so a platform or an SDK of one's own (a fork, a local build, Flutter's engine) compiles through the same action as the VM: rules_dart's own VM provider is built from the resolved Dart toolchain, and another is whatever a rule set or user supplies.

Sources are read through `org-dartlang-root:///` with the exec root and the output directories as roots, so a package whose files are split between the source tree and `bazel-out` (generated parts) resolves without being copied into one directory, and no absolute path reaches the output. `dart_binary` and the web binaries compile the whole program from source: AOT and the web compilers are whole-program compilers.

A target's `package_root` is the directory of the declaration it names (above). A target naming none, and the declaration itself, take it from the BUILD file's directory (`locate_package_root`): that directory when it has no `lib` component, otherwise the directory above its `lib`, so the libraries in `lib/` and in each directory under it are all one package, with one name and one root, and the consumer merges their records as it does any package split across targets. Two `lib` components, or a target with files under its own `lib/` while itself inside one, cannot say which `lib` is the package's, and fail. A `dart_library`'s `srcs` must live under `<package_root>/lib/`, because `package:<name>/x.dart` resolves to `<package_root>/lib/x.dart` and the consumer stages a package by stripping `package_root`. This is checked at analysis time (`check_files_under_package_root`); without it a stray file surfaces only as a missing path inside a `.pkgsrcs` directory at kernel-compile time, naming neither the target nor `lib/`. Generated sources obey the same rule: `declare_file` paths are relative to the _producing_ rule's package, so a codegen target outside the Dart package root emits a path that no longer starts with `package_root`. Targets using `srcs_dir` are exempt — a `copy_to_directory` directory is already assembled, and its directory is the package root.

- `package_config.json` is generated at build time from the `DartInfo` graph to bridge Bazel's dep model with Dart's `package:` URI resolution: a module's lists only its own package, since its dependencies are read from their modules

## Design Decisions

1. **Bazel version**: Bazel 9.x only. bzlmod required.
2. **Platforms**: five **hosts**, for which an SDK is downloaded and a build can run — macos-arm64, macos-x64, linux-x64, linux-arm64, windows-x64 — plus two **cross-only targets** that can be built _for_ but not _on_: linux-riscv64 and linux-arm (armv7). See [Cross-Compilation](#cross-compilation).
3. **Compilation modes**: `dart compile exe` (default), `aot-snapshot`, `kernel`, plus `dart_js_binary` (JS) and `dart_wasm_binary` (WASM) for web. A VM compile is two actions: the front end (`frontend_server`, run once on the entrypoint) produces a kernel, and `dart compile` turns it into the requested output (a `kernel` is the first action's output itself). The front end reads the sources through a filesystem rooted at the exec root (`--filesystem-scheme org-dartlang-root`), because the compiled program keeps the URI of every library outside a package — in stack traces and in the private-name suffixes derived from it — and `dart compile` given a path names the entrypoint `file:///<absolute path>`, so the output would depend on the sandbox directory and output base it was built in. The first action passes the front end what `dart compile` would: the product platform dill (named relative to `--sdk-root`) and `dart.vm.product=true`, which it folds as a constant. It is `frontend_server` rather than `gen_kernel` because it keeps a define value whole (see Command-Line Defines). `frontend_server` prints its protocol (a result line, an identifier, the output path and an error count) even when nothing is wrong, and Bazel shows what a successful action prints, so the action runs it through `kernel_tool frontend`, which reads the protocol and passes on only the compiler's own messages. The targets that build `kernel_tool` (`dart_tool_binary`, `dart_bootstrap_binary`) cannot run through it and run the front end directly, so each of their kernels prints the protocol once when it is built. On macOS the second action runs `dart compile` through `compile_runner`, because gen_snapshot names the file it wrote in the Mach-O symbol table (an N_OSO entry): a new temporary directory for each `exe`, the output path for an `aot-snapshot`. The runner compiles into a directory whose path is the same length on every machine, replaces the name with its last component, and recomputes the ad-hoc code signature over the pages that changed. `compile_runner` is itself a `kernel`, built by a rule without the runner, which breaks the cycle. The `kernel` and `aot-snapshot` outputs are not programs the operating system can start, so in those modes the target's executable is a launcher: a shared, precompiled Dart program symlinked as `<name>` (`<name>.exe` on Windows), which reads `<name>.launcher.json` beside itself, names the VM (`dart`, or `dartaotruntime` for an `aot-snapshot`) and the output by runfiles path, and starts the VM on the output with the runfiles variables set, so that `package:runfiles` in the program finds its files. The configuration is a file rather than the environment so that the target runs the same under `bazel run` and as another target's `data`, which gets no `RunEnvironmentInfo`; `dart_test` and `@rules_dart//dart` (`dart_sdk_binary`) find their configuration the same way. A cross toolchain's SDK runs on the host, not the target, so a cross-compiled snapshot or kernel stays its own executable.
4. **pub.from_lock**: `hosted` and `git` packages are resolved. `resolve` maps a locked package of any source to a workspace target instead. Every `path` package must be named in exactly one of `resolve`, `build_from_pubspec` or `ignored`: `build_from_pubspec` makes it an ordinary spoke (`pub_lock_path_package`) whose files come from the package's directory, which the spoke names by the lock's label and the lock's relative path and resolves when it is fetched, never by an absolute path, since a repository's attributes are part of the extension's result, which must hold on every machine (a lock path that is absolute or leaves the lock's repository fails when the lock is read); its entries are linked one by one by `fetch_pub_path` (`dart/pub/private/pub_path.bzl`, exported for rules_flutter through `pub_lock_package.bzl`), which watches each entry and refuses any Bazel file under them, since a `BUILD` file would make its directory a package the generated globs skip; the spoke is not reproducible. `ignored` gives the package a library repository holding `pub_ignored_package`, which fails analysis with the user's reason, so only a dependency on it fails. A name the lock does not list, a non-`path` name in the two new lists, a name in two of the three, an unnamed `path` package, and two calls mapping one package to different targets or directories fail when the lock is read. Unmapped `sdk` sources produce a warning and are skipped; a fetched package that depends on one fails when its library repository is fetched, naming the dependency, rather than building without it. A git package's source repository (`pub_lock_git_package`) fetches through one helper, `fetch_pub_git` (`dart/pub/private/pub_git.bzl`, exported for rules_flutter through `pub_lock_package.bzl` with `check_pub_git_resolved_ref`), and is an ordinary spoke otherwise: same member, same library repository, same cycles. The lock's `resolved-ref` must be a full 40-hex commit id, checked when the extension reads the lock; anything else names no fixed commit. Bazel's `git_repository` is not used because its bytes depend on the host's git configuration (autocrlf, filters, hooks), which a repository marked reproducible would then share through the repository contents cache. The helper works in two phases with the host `git` (2.14 or newer, pub's own floor), with every client `GIT_*` variable unset when it writes the files (unset, not emptied: git refuses an empty `GIT_ATTR_SOURCE`), since Bazel passes them to repository rules. The fetch keeps the host's configuration, for credentials, proxies and `insteadOf` mirrors, in its files and in its variables (`GIT_SSH_COMMAND`, `GIT_ASKPASS`, `GIT_CONFIG_COUNT` with its keys and values, `GIT_CONFIG_PARAMETERS`): it unsets only the variables that locate a repository, as the host's git lists them in `git rev-parse --local-env-vars` (the list differs between versions, so it is asked for, not written down), except the two that carry configuration, and `GIT_ATTR_SOURCE`. That is safe because the commit is named by its full id and checked after the fetch, and the files are written without the variables. It asks for the one commit, shallowly, and when the server refuses (protocol v0 servers and dumb transports refuse an unadvertised commit) fetches every ref it advertises, as pub's mirror clone does, then checks the commit is there. Writing the files cuts the host off (no system config, an empty `HOME`, `core.autocrlf=false`, `core.eol=lf`, `core.symlinks=true`, an empty hooks directory and attributes file) and reads the whole commit into the index before checking out only the lock's `path`, so every `.gitattributes` in the commit applies, the root's too, as in pub's full checkout. The package directory then becomes the repository root, and symlinks out of it, which in pub's checkout would reach the rest of the repository, are dropped. The repository is created without the host's configuration too, so `init.defaultObjectFormat` or a template cannot change it. A relative `url`, which pub writes for a repository its pubspec names by a relative path, is resolved against the lock's directory. Every hosted package, from `pub.from_lock()` or `pub.package()`, is fetched by one helper, `fetch_pub_archive` (`dart/pub/private/pub_archive.bzl`, exported for rules_flutter through `pub_lock_package.bzl`). Its archive must have a `sha256`, since Bazel reads an empty digest as "do not check"; a lock entry or `pub.package()` without one, and two locks giving one version different digests, fail when the extension runs. It extracts with tar.bzl's prebuilt bsdtar for the host (one repository per platform, only the host's fetched), not the host's `tar`, whose flavour and version vary, and not Bazel's extractor, because pub.dev serves some archives with padding after the gzip stream that Bazel's extractor rejects. It first lists the archive and refuses an entry with an absolute or `..` name, then extracts in a UTF-8 locale so entry names convert the same everywhere. As pub does, it then deletes symlinks that resolve outside the package (or nowhere), judged from the extracted tree. A pub repository (source and library alike) depends only on its attributes and the files it reads, so it is marked reproducible and a new output base reuses it from the repository cache. **A pubspec is read the way pub reads it**, by `read_pubspec` (`dart/pub/pubspec.bzl`), which any repository rule can call, whatever fetched the package and whichever rule set it belongs to: a small Dart program on `package:yaml`, the loader pub uses, prints the pubspec as JSON, and pub's own checks on the fields rules_dart reads (`name`, `dependencies`, `environment`) refuse what pub refuses, with pub's message and the package's name. Its packages, `yaml` and its dependencies, are pinned by version and sha256, fetched with `fetch_pub_archive` outside pub resolution and joined by a hand-written package config; `pub get` never runs. One repository per host platform (`pubspec_reader_<platform>`) compiles the program with that platform's SDK and refuses to on any other host, so a shared cache cannot hand one OS's binary to another; only the host's is fetched. The binary is not part of a package repository's cache key, so every repository that reads a pubspec watches the program's source, and a change to the reader re-reads every package. Lock files stay parsed in Starlark (`yaml_parser.bzl`): the extension needs them before any repository exists, and pub writes them. Each package is two repositories: a source repository (`pub_lock_package`) holding its files and what its own archive states, as a `pub_package_member`, and a library repository (`pub_lock_library`) that reads the pubspec dependencies of every package it reaches, which their source repositories record, and builds the package's dependency cycle — usually just the package — as one `pub_library`, in the library repository of the cycle's first package by name, which every other member aliases. A cycle of several is built only where it is declared (`pub.cycle()`): the declarations are known before anything is fetched, and the extension checks only their form, since whether packages form a cycle is known only once their pubspecs are read; each library repository then checks its own. Cycles are build-wide, as versions are, and the root decides: a root declaration must be exactly the package's cycle at the versions fetched, or the repository fails, giving the declaration to write or remove, so none outlives its cycle; another module's declarations, and rules_dart's curated ones (`curated_cycles()`, `dart/ext/registry.bzl`, beside the curated code assets), apply where they are exactly the cycle and are inert elsewhere, because only the root can fix what its versions made of them. At most one declaration can be exactly a given cycle, so overlapping declarations never compete. An undeclared cycle fails naming its packages, a path through them, and the declaration. Bazel's own cycle error is never what a user sees. What the libraries plan against — every fetched package and version, the `pub.package()` names, the names `resolve` maps, the packages nothing fetches, the cycle declarations — is one index repository, not attributes on each, since a full list on each library would grow the extension's result by the square of the package count. Source repositories read nothing of each other, so the planning never makes a repository wait on itself, and it fetches only what building the package fetches anyway: the lock, which lists no dependencies, is never downloaded whole. The two halves are a public contract, so a rule set whose pub packages carry more than Dart — rules_flutter's carry plugin metadata, native libraries and assets — builds them the same way rather than in a copy: a member rule of its own returns `DartPackageMemberInfo` (`dart_package_member_info()`, `dart/pub/pub_library.bzl`) beside its own providers, a library rule of its own reads both off its members and builds `DartInfo` with `dart_info()`, and its repositories plan with `dependency_graph()` and `dependency_cycle()` (`dart/pub/pub_graph.bzl`), which give the cycle, the repository that builds it, and what it depends on outside it, given that rule set's own declarations and the curated ones, and fail in its own terms (`declare`) for an undeclared or misdeclared cycle; `cycle_declarations_error()` checks the declarations' form in its extension. rules_dart's library rule has no hooks for another kind: what a member carries beyond the contract is that rule set's to merge, in its own rule. Hubs alias every package their locks name, to its library repository. A package declared with `pub.package()` is a source and a library repository too, planned with the locked ones, so it can be in a cycle with them; its library repository is the `@name` the user's `use_repo` names. Its dependencies are those of the pubspec of its archive, as a locked package's are, and a dependency of any fetched package that nothing in the build supplies (no lock lists it, no declaration names it, or a lock lists it as a source nothing fetches) fails when the library repository is fetched, naming both packages. `pub.package()` has no `deps`: a dependency is stated once, in the pubspec. A package `resolve` maps has a library repository too, holding a `pub_resolved_package` that passes the workspace target on once analysis has checked it is that package (a repository rule cannot see providers); every library repository that depends on the package already names that one, so the mapping holds for the whole graph, other modules' locks and rules_dart's own tools included. **One version per package, the highest request**: every statement of a hosted package's version, each module's `pub.package()` and each lock entry alike, is a request, and the highest is built for the whole build, as Bazel's minimal version selection does for modules. The policy is one pure function, `select_pub_version` in `dart/pub/pub_versions.bzl`, which returns messages instead of failing so a unit test reads them and rules_flutter's pub extension applies the same policy with its own commands. Two requests of one version must pin one digest and one registry. A raised request of the root's own is reported at the level of the root-only `pub.settings(check_direct_dependencies = "off" | "warning" | "error")`, default `warning`, naming who raised it and how to raise the root's, as Bazel's `--check_direct_dependencies` does for `bazel_dep`; another module's request raised by a third is what a minimum means and says nothing, while a dependency's `pub.package()` that a root statement raises is noted, also silenced by `off`. A package the root's lock lists from a source with no version order (git, sdk, path) is that lock's for the whole build, over another module's `pub.package()`, whose repository then aliases it, and over another module's lock entry, pub.dev or git, as a root `git_override` is over a `bazel_dep`. A `pub.package()` whose request loses keeps its `@name` repository for its module's `use_repo`, aliasing the winner. `ignore_hook(s)` is root-only for the same reason as the setting: whether a hook matters depends on the programs the build makes, which are the root's. The Dart SDK is a toolchain, not a request: the root's `dart.toolchain` pin is exact, and a dependency asking for a newer one fails, naming the fix, as rules_go does.
5. **Gazelle plugin**: a module of its own, `rules_dart_gazelle_plugin`, rooted at `gazelle/` and released from the same tag and source archive as rules_dart. A `go_library`'s BUILD file loads rules_go in the context of the module that owns it, so a plugin inside rules_dart would make `rules_go` and `gazelle` dependencies of every rules_dart user; in a module of its own, only the users of `@rules_dart_gazelle_plugin//dart` have them. Supports `gazelle:resolve` directive for explicit dependency overrides.
6. **Code generation**: `dart_codegen` (per-file), `dart_aggregate_codegen` (package-level), and `dart_sqlcodegen` (per-file, over non-Dart inputs such as drift's `.drift` files) provide Bazel-native alternatives to `build_runner`. Each runs `package:build` `Builder`s via per-builder AOT shims under `dart/ext/*/`. A Bazel persistent worker amortises Dart-VM startup across requests, but runs each request in a fresh isolate with a fresh `AnalysisContextCollection`: generators keep top-level state meant to last one build (`json_serializable`'s once-per-build pubspec check and its warnings, `source_gen`'s `rootPackageName`), and a request must start from what a one-shot process starts from. The analyzer reads the Dart SDK from a summary each generator writes once with its own `package:analyzer`, as `build_resolvers` does, rather than from the SDK's sources. See [`docs/ext.md`](./ext.md) for the shim contract, Gazelle synthesis, and the guards for generated files checked into a source tree.
7. **Analysis and the format check are an aspect**: `dart_analyze` (`//dart:analyze.bzl`) is applied from `.bazelrc` under `bazel test`, so `bazel run` never pays for it and `bazel test` is where correctness is enforced. Each check has its own actions and its own output group — `dart_analyze` for the analyzer, `dart_format` for the format check — so a repository runs the checks whose groups its `.bazelrc` requests and no others; `no-dart-analyze` and `no-dart-format` opt a target out of one each. It checks only the targets named on the command line (it does not propagate along `deps`) and only each target's own hand-written files — `DefaultInfo` `.dart` files, the nested `DartInfo.srcs` and `DartAnalyzableInfo.entry_srcs` — and resolves its in-repository dependencies without checking them: through their analyzer summaries, staging only the target's own files (see [Analysis Against Summaries](#analysis-against-summaries)), or, with `analysis_summaries` off, by staging them and excluding them through the staged root options file; each is checked when it is itself named. Targets in other repositories are skipped: their module checks them under its own options. Options come from one `dart_analysis_config`, named by the `//dart:analysis_config` label flag, that lists every `analysis_options.yaml` in the repository. All of them are staged at their workspace paths and the SDK's own nearest-file rule picks one per file, so Bazel and the IDE cannot disagree about which options govern a file. The formatter finds its `formatter:` section by the same walk over the same staged tree; the rules_dart-written options file at the staged root ends that walk, so a file no listed options govern gets stock defaults rather than whatever sits above the project. The format check names the target's own files and passes the target's own language version, which selects the formatting style. `dart_analysis_test` applies the same aspect through an attribute to targets a wildcard cannot name (tagged `manual`, fixtures), and depends on both checks' output groups, so their verdict is reached in the build exactly as under `.bazelrc`. An options file's own diagnostics (an unresolvable `include:`) fail only targets with files beneath it; the format runner escalates the formatter's warning about the same, which would otherwise silently fall back to defaults.
8. **Source rewriting**: formatting and `dart fix` reach the workspace the way aspect_rules_lint's fixes and rules_rust's `rustfmt` do: the aspect computes the rewrite as a build output, and a `bazel run` tool builds it over target patterns and writes it back. The format check is two actions: `DartFormat` runs `dart format --output=json` and writes a changes file — for each of the target's own files it would change, the workspace path, the SHA-256 of the bytes it read and the new content — in the `dart_format_changes` group; `DartFormatCheck` fails when that file proposes anything and is the `dart_format` group. A `DartFix` action over the analyzer's staged project writes the same kind of file in `dart_fix_changes`. `@rules_dart//dart/format` and `@rules_dart//dart/fix` are one program (`apply_changes.dart`) run with a different group: it runs `bazel build --aspects=… --output_groups=<group> --norun_validations` followed by the `bazel build` flags and patterns it is given, from the directory `bazel run` was invoked in (Bazel offers a `bazel run` binary no way to read the flags of the command that launched it, so a caller's `--config` reaches the nested build only as an argument, as with rules_rust's `gen_rust_project --config` and hedron's `refresh_compile_commands`), finds the changes files through that build's `--build_event_json_file`, and writes them only if every file still holds the bytes they were computed from and no two targets propose different content for one file; otherwise it writes nothing. So a rewrite is exactly what the check computed: same staged project, same options, same per-target language version. Patterns rather than a rule attribute let a run take `//...`, exclusions and the output of a `bazel query`; taking `bazel build`'s own arguments means a run formats exactly what that build would build, tag filters included. Only the target's own files that Bazel records as `is_source` are eligible for a fix, which keeps codegen output resolvable to its importers without being editable; `dart fix`'s own generated-file heuristic cannot be relied on, since it matches `*.g.dart` and no other name. A change the fixer made to anything else is listed as dropped, and the tool warns about it.
9. **Test runner**: Bazel defines how a test framework honours `--test_filter` (`TESTBRIDGE_TEST_ONLY`), sharding (`TEST_TOTAL_SHARDS`, `TEST_SHARD_INDEX`, `TEST_SHARD_STATUS_FILE`), per-case results (`XML_OUTPUT_FILE`) and time limits (`size`/`timeout`), and where Bazel defines one, Bazel's wins. A `package:test` file run directly implements none of that and applies its own 30-second per-case timeout, so `dart_test` runs such tests under `package:test`'s runner with `--precompiled`: the test is still compiled at build time, from a generated bootstrap that hands `main` to the runner, and the launcher translates Bazel's variables into runner flags, passes Bazel's own limit as the runner's default per-case timeout (`--timeout=<TEST_TIMEOUT>s`, not `none`, which would also override the timeouts a test states on its own cases), and converts the runner's JSON report into JUnit XML. Tag selection is the target's `include_tags`/`exclude_tags` and a run's `DART_TEST_TAGS`/`DART_TEST_EXCLUDE_TAGS`, passed as the runner's `--tags`/`--exclude-tags` so they combine as `package:test` combines them, and a run's `DART_TEST_ORDERING_SEED` is passed as `--test-randomize-ordering-seed`; a run's selection that leaves no case passes, like a filter, with a note listing the suite's tags, which the launcher learns from a second run selecting no case, the runner's only report of them. The runner reads no `dart_test.yaml` (`--configuration` names a file that does not exist): each of its settings has a place on the target or in Bazel. A test runs in its package's root inside its runfiles, as `dart test` runs it and as `go_test` runs in its package directory: the package is the deepest one of the test's own repository, among those its build knows, whose root holds the test file, and with none the repository's root, Bazel's own working directory. The runner gets the test file's path from there, so it reads the file's annotations where the test runs and names the suite as `dart test` does. Where runfiles are only a manifest, the launcher lays out from it, in a scratch directory, the runfiles the test brings: its source, its `data`, and its libraries' resources and `data`, which `dart_test` lists in a file beside the launcher, every repository's at its runfiles path as a tree holds them; it runs there, so what a test reads by its path is where it is on every platform. Its own files (its program, the compiled test and its kernels, the runner and the VM) it finds through the manifest, and what else the manifest lists (a test run as another's `data` is given that test's manifest) is not laid out. Nor is the Dart SDK, which `@rules_dart//dart` in `data` brings whole, 620 MB that would be copied on every run: the test finds it through the manifest, as the launcher finds the VM, and Bazel's way to reach another repository's runfiles is the manifest (`rlocation`) anyway, since a path to them goes through its canonical name. The runner and the test talk over a protocol private to one `package:test` version, so the runner is built from the user's own `package:test`, once, in that package's pub library repository: its public `test` target forwards the library and carries the runner (`DartTestRunnerInfo`), and `dart_test` takes it from its direct deps. A test without `package:test` runs directly and refuses a filter, tags, an ordering seed or shards rather than reporting a selection that never happened. The test runs in the launcher's environment minus the launcher's own `RULES_DART_` variables, so a test that starts another `dart_test` or `dart_binary` from its `data` gives it Bazel's test and runfiles variables and nothing that would make it run this test's kernel. The runner starts from an app-JIT snapshot in a per-machine cache (`--@rules_dart//dart:runner_snapshot`, off by default; `runner_snapshot.dart`), which roughly halves a trivial test's start-up: the VM starts sooner, and the runner's argument, configuration and source-annotation work before the suite loads, about 90 ms from its kernel, is already compiled. The snapshot is never a Bazel input or output: training is not byte-reproducible (event-loop timing and paths reach the compiled code and its type feedback; dart-lang/sdk#64420), so Bazel would see new bytes and rerun every test. It changes only how fast the runner starts, which is what makes a cache outside Bazel acceptable. Its name is the key: the runner's SHA-256, taken once per runner by `dart_test_package`, and the VM's version, OS and architecture, so a changed runner or SDK never starts from an old snapshot. When there is none, the test runs from the runner's kernel, as with the cache off, and the launcher then trains one in a run of its own: the runner on the same suite with a filter that selects no case, which loads the suite and exits, the VM writing the snapshot at exit. Training is not a by-product of the test's own run because a test that ends the VM with `exit()` from its isolate stops the VM writing a snapshot and turns its exit code into 255. A snapshot trained on one test serves another almost as well as one trained on that test, within about 10 ms. The cache is where a sandboxed test can write and every build shares: `/tmp` on macOS, which Bazel's macOS sandbox leaves writable, rather than the home, which a test does not write; `/dev/shm` on Linux, the one shared directory Bazel's Linux sandbox leaves writable; on both, in a directory private to the user; the shell's local application data on Windows, which has no sandbox and whose test environment has no `LOCALAPPDATA`. Each run writes its snapshot under a name of its own and renames it into place, so concurrent first runs need no lock; a claim file only spares them all training. Training keeps the eight snapshots used most recently, about 50 MB each. Every failure is an error naming the flag, never a quiet run from the kernel: a cache that cannot be made or written, a training that writes no snapshot, and a snapshot the VM cannot start the runner from, recognised by the runner's report never being written, which is then removed. It is off by default because only the user knows where tests run: a remote executor may have no writable shared directory, which fails every test, or a fresh one for each action, where each test trains a snapshot it then discards.
10. **Program assets, recorded uses and link hooks**: what a package declares is a fact of the package, the same in every program, and rides `DartPackageInfo`: its data assets (`dart_data_asset`, standing in for what its build hook emits: the id must be the package's own and each name appear once, upstream's rules for a build hook's output), its code assets, its `hook/link.dart` and the ids that hook promises (`link_hook_assets`). What a program ships is one operation over the program, its packages (`program_packages(package, deps)`, its own first, as upstream's hooks runner plans the root package with the rest) and whether it is linked, `dart_program_assets_actions()`, which `dart_program_assets` wraps and every consumer calls, so a bundler, a binary and a test cannot disagree; its result is `DartProgramAssetsInfo`, the same shape linked or not, in which each fact appears once: `data_assets` and `code_assets`, by id, what certainly ships and is known at analysis time, and `link_outputs`, one entry per package whose hook ran (its output directory of data assets, the code assets it chose among, and a file of the ids it kept), which is empty unlinked. Ships-for-certain and candidate never share a field. Upstream's build hook sends its assets to the bundle when linking is off and, by convention, to its own package's link hook when it is on (`ToLinkHook`), which emits what the program needs and nothing else of them ships. So unlinked (a debug build), every declared asset ships and all are known at analysis time; linked, the assets of packages without a link hook ship as they are, and each package's hook gets its declared assets as `LinkInput.assets`, the files as inputs of its action. The uses come from the compiler: `@RecordUse` on a `final class` or a static method makes the AOT compiler write each constant instance and each call's constant arguments that survive tree-shaking. `dart_binary(record_use = True)` passes `--recorded-uses` to the `dart compile` action that tree-shakes — the `exe` and `aot-snapshot` modes — so there is no second compile; the `kernel` mode tree-shakes nothing, so it provides the `{}` the compiler writes when there is nothing to record (`kind = "empty"`), and a hook runs over no uses rather than the rule failing. Linking takes a `DartRecordedUsesInfo`, whose `package` must be the program's own, and runs one action per package with a hook, building the hook's `LinkInput` with `package:hooks` (the uses in `resource_identifiers`) and running it on the exec toolchain's `dart` against a `package_config.json` synthesised from the closure, in which the hook's own package is assembled into one directory of exactly the files Bazel declared for it (its sources, generated and hand-written alike, its resources and the hook; for the program's own package, also the program's own files under its `lib/`, which `DartRecordedUsesInfo` carries), so the hook finds a generated part beside its library and cannot read a file of the package that no target declares, and failing with the hook's own output when it exits non-zero or reports a failure. What a hook emits may depend on the program, and Bazel names every output before anything runs, so a hook's data assets are copied into one output directory per package, except the ids its package promises, which are declared Files and so known at analysis time; the hook must emit every promised id and may emit more. A hook also gets its package's declared code assets, with upstream's code configuration of the target (`config.extensions.code_assets`, which the caller supplies: `vm_code_config` for a VM program; every hook gets it when the target loads code assets, as upstream's VM builds give it), and selects among them: one it keeps ships, one it drops does not, as upstream bundles only what a link hook emits of what was routed to it, so which of them ship is not known until it runs, and they are its link output's candidates rather than `code_assets`. It keeps one exactly as its package declares it, under the same id and link mode: upstream allows a link hook any id, but a program's kernel maps ids to libraries before any hook runs, so a renamed asset would never load, and refusing renames makes the kept set a plain list of ids and every candidate plus `code_assets` the kernel's mapping in every build mode (`program_kernel_code_assets`). A code asset whose file (or, without one, whose link mode) is none of its inputs is native code the hook built, which a hermetic action cannot have, and fails. Native code a package links per program is a package fact of its own, `linked_code_assets` (`dart_linked_code_asset`: a `CcInfo`, a tool and an id), linked by the program step itself: upstream's treeshaking link hooks map the recorded calls of `@RecordUse` `@Native` functions to native symbols and link with `LinkerOptions.treeshake(symbolsToKeep:)`, which exports just those (an ELF version script with `--gc-sections`, a Mach-O exported-symbols list with `-dead_strip`, a Windows module-definition file with `/OPT:REF`); here the tool does the mapping in an action of its own, `link_exports` writes the export file in the format the target's linker reads, and `cc_common.link` links the library with the registered C++ toolchain, its own objects whole as a `cc_shared_library`'s `deps` are, into a library that is the program's own, hermetic and cacheable like any link. Unlinked, it is linked whole, exporting every symbol its own objects define; a Windows DLL exports nothing unless told, so there a module-definition file lists them, written as `cc_binary` writes one under `windows_export_all_symbols`, and one is always passed, empty when nothing is kept, so the linker writes the import library Bazel declares. Its id is known at analysis time either way, so it is in `code_assets`; upstream drops the library when no symbol is kept, which here would make `code_assets` depend on the uses, so a library exporting nothing ships instead. The runner fails, naming what to change, on an emitted asset of another package, an id emitted twice, a name that is not a relative path (its file would be outside the output), two names that differ only in case (one file on a case-insensitive file system) or a name that is a directory of another (a reader listing the directory would see something else), or a promised id not emitted. Its outputs name no path: the directory's contents are the names, and the selection is ids, so the action's output is the same under any output layout and it runs path-mapped. Bazel maps the File objects on an action's command line and never a path written into a file the action reads, except one: a param file, which Bazel writes from the mapped command line. So a consumer is handed the program's assets as a param file that `program_assets_action_args()` arranges (its own `Args`, always a param file, one item per line, behind the one flag `--program-assets`), with directories passed whole, and reads it with `ProgramAssets.read` (`dart/program_assets`), which lists each directory and applies each selection; the line format is documented in the README for readers in other languages, with a conformance fixture, and starts with its name and version so a reader refuses a format it does not know. A `dart_program_assets` target writes the same lines with runfiles paths as its output, its runfiles holding every file, so a test reads a program's assets with no action of its own. Each hook's output directory is a validation output, so a hook that promises nothing still runs and its verdict on the program is never skipped. Bazel stops mapping an action whose inputs would collide once mapped (two configurations' builds of one path); it then runs with unmapped paths, which the param file carries the same way. Each hook runs alone: upstream lets a link hook route assets or metadata to another package's link hook, run in dependency order; nothing here needs it yet, and the runner refuses such output, saying so, rather than dropping it. `dart_binary` and `dart_test` are programs nothing links, and take the code assets they embed (`--native-assets`) from the same operation, unlinked, through `program_kernel_code_assets`, with their own `code_assets` as the program's, which replace a package's under the same id, so the VM and a bundle of the same program cannot disagree. A pub package's link hook is recorded by `pub.from_lock()`/`pub.package()`; only a build hook (`hook/build.dart`), which rules_dart cannot run, counts as an unreplaced hook that fails a consuming binary. Nothing but a linked program runs a link hook, matching upstream, where only a release build links.
11. **Coverage**: Bazel's coverage protocol asks a test to write LCOV tracefiles to `COVERAGE_DIR`, which its coverage runner merges with the LCOV merger the test names (`_lcov_merger`) into `coverage.dat`, keeping the files `COVERAGE_MANIFEST` lists; `--combined_report=lcov` merges every test's. Which files those are is `InstrumentedFilesInfo`: `dart_library` gives its `srcs` and its `deps`', `dart_test` its `main`, `srcs` and `deps`', and Bazel keeps those of targets `--instrumentation_filter` selects. Nothing is compiled differently: the Dart VM counts what runs in any kernel and reports it through its service, so a coverage build compiles the same kernels as a test build, and only the test's launcher configuration and runfiles change, carrying `coverage_converter`, `coverage_collector`, the test's packages' `lib/` directories and the sources Bazel instruments (the test's own and what its deps' `InstrumentedFilesInfo` names), which are in no other build. A `package:test` test's runner gets `--coverage`, under which it starts the VM service in its own process and collects each suite's isolate before ending it; `coverage_converter` then converts what it wrote. A plain-`main()` test runs through the collector, which starts the VM with its service on and `--pause-isolates-on-exit`, collects once every isolate has paused, and lets the VM finish; `exit()` ends the VM without pausing, which leaves nothing to collect and so fails the test. The converter, a public tool (`@rules_dart//dart:coverage_converter`) for any test rule that collects `package:coverage` hit maps from a VM of its own, and `test_coverage` (`dart/private/dart_coverage.bzl`, exported by `utils.bzl` with `COVERAGE_ATTRS`) are what `dart_test` itself uses; they reuse the conversion, so there is one. The converter reports a script by its path in `COVERAGE_MANIFEST`: a library outside a package's `lib/` by the path below the kernel roots its `org-dartlang-root:///` URI holds, a `package:` library through its package's `lib/` directories, and a generated file under its output directory's path. A script the manifest does not list (the SDK, a generated entrypoint, a library left out by the filter) is dropped. The converter reads each reported source from the runfiles, found by the exec path in the file `test_coverage` writes, and leaves out what its `// coverage:ignore-line`, `-start`/`-end` and `-file` comments name, through `package:coverage`'s `filterIgnored`, as `dart test --coverage-path` does; a reported source missing from the runfiles, or an unbalanced marker, is an error, not a report that ignores nothing. Coverage is of lines only.
12. **Package identity**: every repository fetched from a registry or a release says what it holds in Bazel's supply-chain metadata, as rules_python's pip and Gazelle's `go_repository` do: a `package_metadata` target with a purl, which the repository's `REPO.bazel` attaches to every target in it through `default_package_metadata`, so an SBOM tool's aspect reads it from each target's `package_metadata` attribute with no knowledge of Dart. A hosted pub package is `pkg:pub/<name>@<version>` with the archive's `checksum` and, off pub.dev, its `repository_url`; a git package carries the lock's repository, commit and directory as `vcs_url`; a path package is the user's and gets none. The purls are built with the module's own builder (`pub_hosted_purl`, `pub_git_purl`, exported for rules_flutter), from the repository's attributes alone, so the repositories stay reproducible. The Dart SDK and cross-compilation repositories are `pkg:generic/dart-sdk@<version>`: the purl spec has no type for the SDK, and its `github` type names a source tree, not the prebuilt archive. Native code built in place of a build hook is identified as what it is built from, never as the Dart package: SQLite as the BCR `sqlite3` module (unversioned, since the module graph picks the version), the BoringSSL webcrypto vendors by its revision, and webcrypto's own C glue, which is in its pub archive, as that package. No pub package states a license kind, so no `license` attribute is generated; the license text a Flutter `NOTICES` needs at analysis time stays `license_file`, since the standard's `license` exposes its text only through a JSON file an action would have to parse.
13. **Packages of the workspace that import each other**: Dart allows a cycle between packages and Bazel allows none between targets, so the packages of a cycle are one target, as Java packages that refer to each other share one `java_library`. Each package is a `dart_package_member` (its `lib/` files and its declaration, checked as a `dart_library`'s are through the same `library_sources()`), which is no `DartInfo`, so nothing but its cycle can depend on it. A `dart_package_cycle` builds the members as one library carrying several package records, each with its own root and language version, through `package_cycle_library()` (`dart/private/dart_package_cycle.bzl`), which `pub_library` is a thin layer over, so one implementation builds several packages into one library. The rest of rules_dart already treats every record of a target as its own (`own_packages()`): the import check, the analyzer and the formatter split by package root, and the declaration agreement check merges each record with every other for its root. A cycle target differs from `pub_library` by being runtime-independent only when marked, as a `dart_library`, by giving coverage, and by checking itself: its import check runs with `--check-cycle`, which builds the graph of what the members import, every branch of a conditional import counted, and fails unless the members are one strongly connected component. A member no other member reaches, or two cycles in one target, fails, naming what to change; an imported package that no dependency provides is named as the member that may be missing, since a package closing the cycle cannot be a dependency without a cycle of targets. Cycles are off by default: an undeclared one is two libraries in each other's `deps`, which is Bazel's own cycle error, or one library missing the other, whose import check message points at `dart_package_cycle`. Gazelle writes the targets from a `# gazelle:dart_cycle` directive and detects undeclared cycles itself, since it sees every package's imports before it writes anything. A cycle between a workspace package and a pub package is built in the pub graph: the workspace package joins it through `build_from_pubspec`, and `pub.cycle()` declares the cycle. Code generation inside a cycle reads the members, not the cycle: a codegen rule's `deps` take `dart_package_member`s beside libraries (`codegen_deps()`, `dart/private/codegen_deps.bzl`), so its analyzer sees every member's hand-written sources under their own package names, as build_runner resolves a whole package graph and as the analysis aspect analyzes a cycle as one unit. A member therefore holds only hand-written files, and the cycle's `srcs` holds what generators write, each file assigned to the member whose `lib/` holds it and checked against its generator's declaration (`codegen_identity_error`). Completeness is checked rather than assumed: a codegen target that reads members runs the import check over their sources against its `deps` (`--generator-input`, which leaves out the parts the generators have yet to write), so a missing member or library fails the build instead of resolving a type to nothing. Gazelle gives each such codegen target every member and the members' outside imports, at resolve time, when every member's imports are known.

## Per-compiler code

Dart chooses between native and web code with a conditional import on `dart.library.js_interop`, and between dart2js and dart2wasm inside a function body with `bool.fromEnvironment('dart.tool.dart2wasm')`. It cannot give the two web compilers different declared types or files: conditional imports ignore `dart.tool.*` and `-D` defines, and the only library tests that separate them (`dart.library.html` and friends) are deprecated. That is what the runtime constraint adds.

- **The constraint.** `//dart/constraints:runtime`, a `constraint_setting` with values `vm` (its `default_constraint_value`), `js` and `wasm`, the `@TestOn` selectors package:test has for the Dart VM and the two web compiler families (`vm` names its runtime, `js` and `wasm` what the compiler emits). The setting is named for what the code runs on: the VM, a JavaScript engine, a Wasm engine. That is coarser than package:test's `Runtime` (`chrome`, `node`, …), and coarser than a compiler: DDC and dart2js both build `js`, so a debug web build needs two configurations, not three. The default means every platform that never mentions it (the host, Android, iOS, a user's own) is a VM platform, and a `select()` keyed on `//dart/constraints:js` or `:wasm` takes its default branch there. `@platforms` has no value for JavaScript, and no other module publishes one; rules_go defines its own (`js` under `@platforms//os:os`). This is a setting of its own rather than a value of `os` or `cpu` because the runtime is orthogonal to both: a rule set building Rust or C for the same page (frustrate) chooses its own `cpu:wasm32` platform, and a Dart web platform must not decide it.
- **The platforms.** `//dart/platforms:js` and `:wasm` carry the constraint and nothing else: no `os`, no `cpu`, no `flags`. Native code reached on one, outside a reset, fails toolchain resolution rather than building for some other wasm target. A user's platform can stand in for either, by the binaries' `platform` attribute, as long as it carries the value; the binary checks that through `ctx.target_platform_has_constraint` on its transitioned edge and names the missing value. It should carry no `flags`: a platform's flags are applied when a transition selects it and are not undone when the reset leaves it, so the targets beneath the reset would build in a configuration of their own, with the flag still set.
- **Set by the binaries, on `deps`.** `dart_js_binary` and `dart_wasm_binary` carry the transition on their `deps` edge, not as their own `cfg`: the binary stays in the top-level configuration, its outputs stay under `bazel-bin`, and only what it depends on is built for the web platform. This is the shape of rules_go's `goos`/`goarch` attributes, applied to an edge. A library chooses a variant with `select()` in `deps`; variants are separate targets of packages with one `package_name`, so the import does not change. Which binary is built decides which branch is.
- **Resets.** Every target under a web binary is configured for the web platform, whether or not its outputs depend on it, so without more, pub packages, codegen and the C or Rust under a code asset would be built once per compiler, and the native ones would not resolve a toolchain at all. Rules whose outputs cannot depend on the compiler therefore go back on their incoming edge to the platform the build had before the web transition: `dart_codegen`, `dart_aggregate_codegen`, `dart_sqlcodegen`, `dart_code_asset` and `dart_data_asset` always (`non_dart_transition`, which also turns off `track_creation_locations` and clears an executable's environment declarations; see [Creation Locations](#creation-locations)), `pub_library` always (`runtime_reset`), and `dart_library` when it says `runtime_independent = True` (`runtime_reset_when_independent`), which the generated BUILD file of every pub repository, from `pub.package()` or `pub.from_lock()`, does. A transition cannot see `--platforms` as it was before another transition replaced it, so the web transitions record it in a private setting (`//dart/private:platforms_before_web`, `scope = "target"`) and the reset restores it and clears the record; the result is the plain build's configuration exactly, so one configured target serves every binary and any VM build. This is rules_go's mechanism for its own settings: `go_transition` records `original_*` settings and `non_go_transition` restores them and clears the record, for the same two reasons (no rebuilds from configuration changes, and no stale value on a later path). What still forks is the first-party libraries on the path to a `select()`, the hub aliases and the toolchain filegroups; none of them runs an action, so the cost is analysis, and sharing needs no path mapping.
- **Other rule sets** use the same transitions from `//dart:utils.bzl`: `cfg = non_dart_transition` on a rule nothing of which is compiled Dart (a native or Rust module, a code generator, a data asset), `cfg = runtime_reset` on a Dart library that is always independent (a pub package), and `RUNTIME_INDEPENDENT_ATTR` with `cfg = runtime_reset_when_independent` on one that wraps both pub packages and first-party code. A rule that builds Dart for a web platform does it with `web_platform_transition` (its `platform` attribute), `web_platforms_transition` (a split over its `web_platforms`), or `web_platform_settings` in a transition of its own, never by setting `--platforms` alone, which would leave the resets nothing to restore. An analysis test, whose `config_settings` is a fixed dict, uses `web_platform_config_settings(platform)`, the same settings computed from the platforms the test is built for (the host's by default; a dict cannot read them). A rule compiling one app for several compilers stages each branch in a target configured for that branch: staging two branches inside one target declares the same `<name>.<package>.pkgsrcs` outputs twice.
- **Codegen cannot vary by compiler.** A reset rule's attributes are resolved after its incoming transition, so a `select()` on the runtime in a codegen target always sees `vm`. A generator emits every variant, once each, and the first-party library selects.
- **No compiler.** Code with no VM variant says so with `target_compatible_with = select({vm: ["@platforms//:incompatible"], default: []})`, the form Bazel's platform documentation gives for "compatible with everything except", and code with no web variant with `target_compatible_with = [vm]`; Gazelle writes both from `@TestOn`. Wildcards skip web-only code on the host, and a VM program or test reaching it is incompatible: by name, Bazel refuses it with the dependency chain ending in "target platform (…) didn't satisfy constraint @platforms//:incompatible"; in a wildcard it is skipped, silently. The `dart_analyze` aspect never reaches it from `//...`, so `dart_analysis_test(web_platforms = [...])` checks it, once per web platform listed. There is no `web` constraint value: the web platforms would carry it beside their compiler's, a second statement of one fact that a platform of a user's own could make inconsistently, and that apple_support's `target_vendor` shows is not relied on (rules_swift selects on apple_support's `configs:apple` group, which also matches each Apple CPU's own settings). A skylib `config_setting_group` over `js` and `wasm` would be a key no shorter than `vm`, and a second way to write it.

## Cross-Compilation

Dart's AOT compiler supports cross-compilation via `--target-os` and `--target-arch` flags on `dart compile exe` and `dart compile aot-snapshot`. The host SDK compiles for the other platforms: no SDK for the target is downloaded, only the two binaries a cross compile needs (below).

### How It Works

Each SDK repository generates both a **native** `dart_toolchain` target (no `target_os`/`target_arch`) and **cross** `dart_toolchain_cross_{target}` targets for each supported cross-compilation pair. The toolchains repository registers:

- **Native toolchains** (5): `exec_compatible_with` and `target_compatible_with` match the same platform
- **Cross toolchains** (18): `exec_compatible_with` = host, `target_compatible_with` = cross target
- **Exec-tools toolchains** (5): `exec_compatible_with` = host, `target_compatible_with` omitted — for every action whose output is the same whichever host runs it (see [Toolchain Types](#toolchain-types))
- **Outline and analyzer toolchains** (1 each): unconstrained, of the SDK's version

When `--platforms` is set, Bazel's toolchain resolution picks the cross toolchain. `DartSdkInfo` carries `target_os`/`target_arch`, which `dart_compile_action` passes as `--target-os`/`--target-arch` flags.

A cross compile also needs two binaries the SDK does not ship: the pair's `gen_snapshot_{host}_{target}` and, for `exe`, the target's `dartaotruntime_{target}`. Left alone, `dart compile` downloads them at action time into `$HOME/.dart/dartdev/sdk_cache/{version}`, which a sandbox without network or a remote worker cannot do. Instead each pair has a `dart_cross_tools` repository that fetches both with pinned checksums (`CROSS_TOOL_VERSIONS` in `versions.bzl`) and lays them out as that cache. The cross `dart_toolchain`'s `sdk_cache` names it, `DartSdkInfo.cross_tools` carries the files and the directory above the cache, and the compile action takes the files as inputs and that directory as its `HOME` (`APPDATA` on Windows). dartdev finds them there and makes no request. The repository is fetched only when its pair is used.

Two tables in `dart/private/toolchains_repo.bzl` drive this. `PLATFORMS` holds the hosts: each entry downloads an SDK, so each costs one SHA-256 per pinned version in `versions.bzl`. `TARGET_ONLY_PLATFORMS` holds destinations that are never built _on_ — a cross toolchain reuses the **host** SDK's `dart` binary, so no SDK is fetched for the target; its cost is the cross binaries above, one `gen_snapshot` checksum per host that reaches it and one `dartaotruntime`, per pinned version. `TARGET_PLATFORMS` is the union and is what a cross target is looked up in. `linux-riscv64` and `linux-arm` are target-only because Bazel publishes no release for either CPU, so neither can ever be an exec platform.

The SDK, cross-tools and toolchains repositories depend only on their attributes (pinned URLs and checksums; the platform is an attribute, never read from the host), so each is marked reproducible and a new output base or worktree reuses the extracted SDK from the repository contents cache rather than downloading and extracting it again. A rule here that read the host would break that sharing, so `dart/tests/repositories_reproducible_test.bzl` runs each against a context that offers no host access.

### Supported Cross-Compilation Matrix

| Host (exec) | Target                                           |
| ----------- | ------------------------------------------------ |
| macOS arm64 | linux-x64, linux-arm64, linux-riscv64, linux-arm |
| macOS x64   | linux-x64, linux-arm64, linux-riscv64, linux-arm |
| Linux x64   | linux-arm64, linux-riscv64, linux-arm            |
| Linux arm64 | linux-x64, linux-riscv64, linux-arm              |
| Windows x64 | linux-x64, linux-arm64, linux-riscv64, linux-arm |

`linux-arm` is Dart's armv7 hardfloat target and is selected by `@platforms//cpu:armv7`. Note `@platforms//cpu:arm` is an **alias for `aarch32`** — a different constraint value — and constraint matching has no subtyping, so a platform declaring `:arm` will not resolve the toolchain.

### Usage

Define a platform and set `--platforms`:

```python
# BUILD.bazel
platform(
    name = "linux_x64",
    constraint_values = [
        "@platforms//os:linux",
        "@platforms//cpu:x86_64",
    ],
)
```

```sh
bazel build //:my_binary --platforms=//:linux_x64
```

### Limitations

- Only `exe` and `aot-snapshot` compile modes support cross-compilation. `kernel` is a VM format and ignores target flags.
- `dart_js_binary` and `dart_wasm_binary` output is platform-independent — no cross-compilation needed.
- `dart_test` is built for the target and runs where Bazel runs any test, as `cc_test` does; running it on another host is a platform choice (`--platforms`, or a platform transition on the test).
- Native **code assets** on linux-riscv64 and linux-arm work only if you supply a cc toolchain for that CPU; rules_dart ships none. The ABI mapping is in place (`linux_riscv64`, `linux_arm`), so rules_dart itself will not block you — an unresolvable cc toolchain surfaces as Bazel's own error.

## SDK File Sets

The SDK is ~1,050 files and 620 MB, and an action or a test reads a few of them: running a kernel reads `bin/dart` and `bin/dartvm`, `dart compile exe` five files, `dart analyze` the server and the `dart:` sources. Every input is linked into a sandbox and, under remote execution, listed, hashed and materialised, so each use takes only its own files. `SDK_FILE_SETS` in `dart/toolchain.bzl` lists them by use as glob patterns under the SDK root: `run` (a kernel or a script, in the VM), `aot_run`, `aot_compile` (`exe`/`aot-snapshot`), `kernel` (the front end run directly; such an action takes only the files it names), `format`, `analyze` (also `dart fix`), `codegen` (what `package:analyzer` reads of the SDK it is given, which a generator summarizes), `dart2js` and `dart2wasm`. `dart_sdk_files` declares one filegroup per set over an SDK in a package and collects them, with the whole SDK, into a `DartSdkFilesInfo`, which the toolchain hands on as `DartSdkInfo.files`. Being a macro over any directory laid out as the SDK archive is, it serves another copy of the SDK as well, such as the one Flutter bundles.

The sets were found by running each use against a copy holding only its set and taking away one file at a time. A copy, not links: the `dart` launcher looks for the VM and the snapshots beside its resolved path, so through links, as in a local sandbox or a symlinked runfiles tree, it finds the whole SDK, and a short set shows only on a remote executor. `//dart/tests/sdk_files` keeps both facts: `sdk_file_sets` pins each set's files on the pinned SDK, and `sdk_files_test` runs each use against a copy of its set.

A `dart_test`'s runfiles carry the `run` set and no more. A test that runs SDK commands itself (`dart compile`, `dart analyze`, `dart format`) adds `@rules_dart//dart` to `data`, which carries the whole SDK; `@rules_dart//dart` (`dart_sdk_binary`) and the toolchain's own `DefaultInfo` are the only places that do.

## Toolchain Types

rules_dart exposes **four** toolchain types, registered together by `dart_register_toolchains` (so `register_toolchains("@dart_toolchains//:all")` picks up all four):

- **`//dart:toolchain_type`** — target-configuration. Used where the output is machine code for the target or runs on it: `dart_binary`'s `dart compile exe|aot-snapshot` step, the VM a `dart_test` runs on, `dart_sdk_binary`'s executable, and the `vm_kernel_sdk` the module compiles take their platform files from. Registered native (exec == target) and cross (exec = host, target = cross target) — so resolution depends on the build's target platform, which is correct for compilation.

- **`//dart:exec_tools_toolchain_type`** — exec-configuration. Used by every action whose output is the same whichever host runs it: kernel modules, entrypoints and links, whole-program kernels, import checks, the `dart_analyze` aspect, `dart_js_binary` and `dart_wasm_binary`, and the code generators (`dart_codegen`, `dart_aggregate_codegen`, `dart_sqlcodegen`). Its toolchains are registered one per host platform with `exec_compatible_with` pinned and **`target_compatible_with` omitted**, so each matches _any_ target platform. Both types reuse the same native `dart_toolchain` (the host SDK) — there is no separate SDK download.

- **`//dart:outline_toolchain_type`** — the outline stripper of the SDK's version (see [Dart Compilation Model](#dart-compilation-model)), one per registered SDK version and unconstrained, since the stripper is built from source for whichever host builds modules. Resolved only by `vm_kernel_sdk`, beside `//dart:toolchain_type` in the same order of registration, which must yield the same version.

- **`//dart:analyzer_toolchain_type`** — the summary analyzer of the SDK's version (see [Analysis Against Summaries](#analysis-against-summaries)), one per registered SDK version and unconstrained like the outline toolchain: it is built from the SDK's own `pkg/analyzer` and `pkg/linter` for whichever host builds it, and resolved by `//dart/private:summary_analyzer`, which checks its version against the Dart toolchain's.

The second type is what lets those actions run on a different host from the target: a remote Linux executor building for a Mac, say. They run in the `portable` execution group (`dart/private/exec_groups.bzl`), which resolves to the first registered execution platform with a Dart SDK, and the tools they run (`kernel_tool`, the `vm_kernel_sdk`, a codegen rule's `generator`, the analyze, format and fix runners) are built for that group's host with `config.exec("portable")`. Every action either runs in a named group or, like `dart compile exe`, names the toolchain its executable comes from, so the rules work with Bazel's `--incompatible_auto_exec_groups` on or off. A `dart_test` run is placed as any Bazel test's is, by Bazel's own `test` execution group, on a host matching the target, and everything it runs is built for the target: the launcher, the target toolchain's VM, `data` and native code assets. Running it on another host is building it for that host's platform (`--platforms`, or a platform transition on the test), as for `cc_test`. The VM resolves the kernel's `relative` asset paths against the kernel's real location: the output tree when runfiles are symlinks, the runfiles tree when they are copies (a remote executor). Those agree only for files in the kernel's own configuration and repository, so the test links each library in beside its kernel, and the launcher puts each beside the kernel list it writes at each run (see [Dart Compilation Model](#dart-compilation-model)); a `dart_binary` likewise links its libraries into `<name>.native/` beside the executable, so the executable and that directory, copied together, still run.

Those actions are also the same in every configuration that builds the same library: a Flutter app's Dart for Android, iOS and macOS, a tool built for the exec host and for the target. Every rules_dart action declares `supports-path-mapping`, so under `--experimental_output_paths=strip` Bazel names each configuration's output directory `bazel-out/cfg/bin` in the action, and one result serves them all. That holds only while no path naming a configuration reaches an action other than as a `File`: arguments are `File`s or come from them through `map_each` (`add_kernel_roots` derives the kernel filesystem roots that way), and no generated input names one. Kernel package configs name packages by `org-dartlang-root:///<package_root>/` and every VM compile addresses its entrypoint the same way, relative to the roots; staged package configs use paths relative to the config file; a module's location reaches the link step from its manifest, as the link step sees it, not from what the entry compile saw. `PATH_MAPPING` in `utils.bzl` is the requirement for a downstream rule's actions that keep the same rule. Bazel runs a path-mapped action only in a sandbox or remotely, so the flag suits Linux, macOS and remote execution; on Windows, which has no sandbox, it fails the build (`requires sandboxing due to path mapping`).

This split is why codegen resolves even under a target platform rules_dart registers no compile toolchain for — e.g. a downstream Flutter build that puts the whole graph on `@platforms//os:ios` or `:android`. Were codegen on `//dart:toolchain_type`, it would fail with "No matching toolchains found" for those targets even though the generator runs fine on the host. (Regression-guarded by `e2e/examples/codegen/foreign_platform`, which builds a codegen target under a synthetic toolchain-less platform.)

Registering `@dart_toolchains//:all` registers all four types. A module that registers _specific_ dart toolchains by hand must also register the `*_exec_tools_toolchain` targets, without which no portable action resolves a toolchain, and `outline_toolchain` and `analyzer_toolchain`, without which a module compile fails unless `outline_kernel` is off and an analysis fails unless `analysis_summaries` is off, each error naming its flag.

## Compilation Modes

Bazel's `-c` flag (`fastbuild`, `dbg`, `opt`) controls compiler flags automatically. Rules read `ctx.var["COMPILATION_MODE"]` and map it to Dart compiler flags. Per-target overrides are available via the `dart_compile_flags` and `defines` attributes; `dart_test` takes `defines` only, since its compile mode is fixed.

### Flag Mapping

**dart_binary (exe / aot-snapshot)**

| Bazel Mode  | Flags                                                 |
| ----------- | ----------------------------------------------------- |
| `fastbuild` | _(none)_                                              |
| `dbg`       | `--enable-asserts`                                    |
| `opt`       | `--extra-gen-snapshot-options=--optimization_level=2` |

**dart_binary (kernel)**

A `kernel` keeps its asserts, and its launcher passes `--enable-asserts` to the VM that runs it.

| Bazel Mode  | Flags              |
| ----------- | ------------------ |
| `fastbuild` | _(none)_           |
| `dbg`       | `--enable-asserts` |
| `opt`       | _(none)_           |

**dart_js_binary**

| Bazel Mode  | Flags                              |
| ----------- | ---------------------------------- |
| `fastbuild` | _(none — dart2js defaults to -O1)_ |
| `dbg`       | `--enable-asserts -O0`             |
| `opt`       | `-O2`                              |

**dart_wasm_binary**

| Bazel Mode  | Flags              |
| ----------- | ------------------ |
| `fastbuild` | _(none)_           |
| `dbg`       | `--enable-asserts` |
| `opt`       | _(none)_           |

### Per-Target Attributes

- **`dart_compile_flags`** (`string_list`): Extra flags appended after mode defaults. Appears last so user flags override defaults (e.g., `-O4` after `-O2` — dart2js uses last-wins). For the VM modes, front-end flags (`--enable-experiment`, `-D`/`--define`) go to the front-end action instead, since `dart compile` accepts them on a kernel and ignores them; `--verbosity` goes to both.
- **`defines`** (`string_list`): Entries in `key=value` format. Each becomes a `-Dkey=value` flag passed to the compiler. These are resolved by the front end during constant evaluation, so they must reach the action that compiles source — for the VM modes that is the front-end action, not the `dart compile` step that consumes its kernel.

### Analysis Workers

`--@rules_dart//dart:analysis_worker` (on by default) runs analysis as Bazel persistent workers (`supports-workers`, protobuf protocol, singleplex), their arguments in an always-on param file. With `analysis_summaries` on, the default, the summary and analyze actions run the summary analyzer's worker (see [Analysis Against Summaries](#analysis-against-summaries)); the analysis-server worker described here runs the fix actions, and the analyze actions with summaries off. A worker keeps one analysis server, which `analysis_host.dart` runs from the SDK's JIT snapshot as an isolate of one process started with the SDK's VM, `dartvm`, not the `dart` launcher, which on Windows runs the VM as a child process that outlives a kill of the launcher: ending that process ends the server, so the server is never asked to shut down. The host ends itself when its parent is gone, on SIGTERM (not on Windows, which has no such signal), or when the server ends, and removes its cache, which lives in the worker's temporary directory (`dart_analysis_worker-<pid>-<n>`): a worker writes only there and in its working directory, which Bazel cleans for each sandboxed request, and a hardened sandbox gives each worker a `/tmp` of its own. The host checks once a second whether its parent is gone. On macOS and Linux it sees its parent id change, as a process whose parent dies is handed to another. Windows hands nothing on, so at start-up the host finds its parent in a process snapshot, opens a handle to it and asks that handle whether the parent has ended (`WaitForSingleObject` with a zero timeout), through `dart:ffi` against `kernel32`. The handle is held for the host's life because a process id is not: Windows reuses ids, so a parent found again by id could be a stranger. A parent already gone at start-up, or whose id a younger process now holds, counts as gone. `analysis_host_test` kills the parent of a running host on every OS. A worker stops its server with SIGTERM, so the host removes the cache even if the worker is killed meanwhile, and a starting worker removes the caches of workers that are gone, which a kill of both together leaves. A server serves one SDK, known by its `version` file and server snapshot rather than its path; it is replaced when a request names another SDK, after a request that ran analyzer plugins (they keep state in the cache by path), and when it exits, which fails no request: the request is retried once on a fresh server. It stops after a minute without a request, so it lives within a build; the worker stays. Each analyze request first drops every analysis root and then sets the request's project alone, which rebuilds the server's contexts and empties its file content cache; what the server keeps across requests, its byte store, is keyed by content. A fix request computes bulk fixes, which build their own contexts, and removes the overlays it gave the server. `analysis_restage_test`, in the `deep` tier, is the guard: projects restaged and edited at the same paths, through one worker, each against a fresh `dart analyze`. Off, or when Bazel runs an action without a worker, the runner runs once: `dart analyze` or `dart fix --apply` when off, else a server for that one action.

### Analysis Against Summaries

`--@rules_dart//dart:analysis_summaries` (on by default) gives analysis an early cutoff. A library's summary is produced the way rules_go produces export data and Java header jars: `dart_info()` (`dart/private/dart_summary.bzl`) declares, in the rule building the library's `DartInfo`, the action writing the analyzer's package bundle of its own libraries, linked against its dependencies' bundles and an SDK summary, and `DartInfo.summaries` carries it with its dependencies'. Nothing builds a bundle until an analysis reads it. An analysis reads the bundles off the provider it stages, never by walking attribute edges, so a target that reaches its libraries through another rule set's providers (rules_flutter's Apple bundle, through rules_apple's) is analyzed like any other. What keeps a bundle from being written (no analyzer for the SDK, a rule that does not declare `SUMMARY_ATTRS`, two SDK embedders) is carried in the provider and fails only the analysis that needs it, naming the flag. A library's `analysis_deps` (Flutter's `sky_engine`) are read by its bundle and not compiled, so `dart:ui`, which only `sky_engine`'s `_embedder.yaml` gives the analyzer, resolves in the bundles of the libraries that import it. `DartInfo.analysis_only` carries them, with what they reach, to every library above, so an analysis from source (summaries off, and the fix actions) and a codegen action stage them beside the compile closure and resolve `dart:ui` alike. The summary analyzer is itself built of Dart libraries, so its toolchain builds it with summaries off. A bundle holds declarations and their resolution, not bodies, offsets or comments, so a body or comment edit leaves its bytes unchanged and Bazel's action cache stops there; adding any declaration, a private one included, changes it. The analyze action then stages only the target's own files (its generated ones included, which no bundle holds as separate libraries) with the options, leaves every other package out of the package config, and resolves each import through the bundles, which the analyzer consults before the package config. Every bundle the target's dependencies reach is passed, not only its direct dependencies': a bundle names the libraries its libraries import rather than holding them, and the analyzer reads a library's imports as it reads the library, so a dependency's bundle cannot be read without those below it. That is rules_go's `importcfg` and Java's transitive header classpath, and like them the list goes in a param file (always for a worker, and once it outgrows the command line without one). The analyzer reads each bundle's bytes and index up front but builds elements only for the libraries resolution reaches, so a bundle nothing imports costs its read and no more; each request still builds a fresh context, and keeping bundles across a worker's requests would hold them in the worker for no saving beyond that read. The SDK is read from its summary alone, so no SDK file is an analysis input.

Nothing in the SDK reads bundles: the SDK's analyzer has no build mode, and `package:analyzer` exposes bundles only under `src/`. The summary analyzer (`dart/private/tools/summary_analyzer.dart`) is built per SDK release by `dart_analyzer_source`, on that release's `pkg/analyzer`, `pkg/linter` and `pkg/_fe_analyzer_shared` from its tag archive, unmodified, with their pub dependencies from `@ext_pub_deps`, as `dart_kernel_source` builds the outline stripper. It prints what `dart analyze --fatal-infos` prints, validates pubspecs, options files and Android manifests as the server does, and runs as a singleplex persistent worker with a fresh context collection per request. A summary action fails when its bundle lacks a library it was asked for, which the analyzer otherwise skips silently.

The analyzer answers differently against bundles in known places, and the tool fails the action wherever it can tell: an exception from analysis, or one the analyzer catches and logs (a lint rule's); the `base`/`final` subtype check, which gives up without the supertype's offset, re-decided on the element model; `prefer_relative_imports`, which needs an imported file's path, for same-package imports from a bundle; and `comment_references` diagnostics naming what a doc import from a bundle provides, since the analyzer resolves doc imports only from source. Analyzer plugins and `fix_data.yaml` validation live in the analysis server and are refused. Context messages that point into a dependency lose their location; the diagnostic is unchanged. `dart fix` stays on the SDK's server, from source.

### Command-Line Defines

`--@rules_dart//dart:extra_dart_defines=KEY=VALUE` appends environment declarations to every Dart compile, after any target-level `defines`. It is repeatable — one define per occurrence — so a `.bazelrc` config group can point a whole build at an environment without editing BUILD files, reaching binaries, tests, and web targets alike. On a key collision the flag wins, because every Dart compiler takes the last `-D` for a repeated key. The flag describes the program being built, so it is declared `scope = "target"`: Bazel resets it on every exec transition, whoever's rule makes it, and a build tool is compiled without the app's defines and is not rebuilt when they change. The same holds for the other settings no tool reads (`module_defines`, `track_creation_locations`, `split_debug_info`, `kernel_list`, `runner_snapshot`, `analysis_worker`, `analysis_config`). `modular_kernel`, `outline_kernel` and `analysis_summaries` keep Bazel's default and reach tools: they choose how any Dart library is compiled or analyzed and which toolchains are fetched (the summary analyzer is resolved in the exec configuration of the analysis actions), and turning one off as an escape hatch has to cover the tools too.

No define keys are reserved. rules_dart maps compilation mode to `--enable-asserts` and gen-snapshot options, and sets only the `dart.vm.*` defines `dart compile` itself sets, ahead of the user's, so a user value wins as it would under `dart compile`. (rules_flutter reserves `dart.vm.product` and friends because its build does set them.)

One caveat, inherited from the Dart SDK and shared by the `defines` attribute: `kernel_worker`, the compiler of a `dart_test`'s modules, splits a define **value** on commas, so `-DA=x,y` would reach the test as `A=x`. `frontend_server`, which compiles a `dart_binary` (in every mode) and a test's entrypoint, keeps the value whole, and so do `dart compile js` and `wasm`. A `dart_binary` therefore accepts a comma, and a `dart_test` refuses one, on both of its compile paths (the modular one and the whole-program one that `modular_kernel=false` selects, so that setting never changes what a define means), rather than build a test that silently sees a shorter value. Encode such a value (base64, say) and decode it in the test. The flag is declared `repeatable` so that Bazel itself never splits them — the limit is the compiler's, not the build system's.

### Creation Locations

`--@rules_dart//dart:track_creation_locations` (off by default) compiles every Dart kernel for the VM with the front end's `--track-creation-locations` transform (`--track-widget-creation` is an alias of it). The transform gives the constructors of a tracked class (Flutter's `Widget`, or any class annotated `@pragma('track-creation-locations')`, including its subclasses) a hidden parameter, and passes the location of the call at every call site it compiles. `CreationLocation.of(object)` in `dart:developer` reads the location back.

The transform changes a tracked class's constructor signatures, so a program works only if every library and its entrypoint are compiled with the same setting. A single flag, not an attribute per target, is what guarantees it: the flag reaches each `dart_test` module compile (the `module` command of `kernel_tool`, run by the `dart_module_aspect` for the dependencies and by `dart_test` for its own files), the entrypoint compile (`entry`), and the whole-program compile of `dart_binary` (and of `dart_test` under `modular_kernel=false`). Off, no argument is passed, so command lines and cache keys are those of a build without the flag. The flag has `scope = "target"`, so tools built in the exec configuration are never compiled with it. A rule nothing of which is compiled Dart turns it off on its incoming edge (`non_dart_transition`: codegen, code assets, native modules), so one build reaching such a target from an app and from a test that tracks locations configures it once. A library does not, `runtime_independent` or pub alike: its modules are compiled in its own configuration, and a module compiled without the transform crashes against one compiled with it (`NoSuchMethodError` on the tracked constructor). A rule set that sets it from its build mode does so with a transition on the flag. It applies to the VM compiles only: `dart2js` and `dart2wasm` are not affected.
